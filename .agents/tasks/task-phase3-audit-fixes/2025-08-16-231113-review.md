# Audit hardening v2: all prior issues resolved, residual concerns

This is the second review pass of the Phase 3 audit fixes. All five issues from the v1 review have been addressed: `get_clients_for_bssid` callers now unpack tuples correctly, the deauth loop uses the karma sleep-and-retry pattern, the overbroad `threading.enumerate()` join is gone, the redundant import is removed, and `should_deauth_with_rssi` uses `self.rssi_threshold`. The overall change adds error handling around `sendp` calls, introduces Windows platform warnings, enhances the EAPOL classifier with group key support, threads RSSI data through the pipeline, adds rogue AP input validation and startup rollback, and rewrites the orchestrator teardown as a clean engine-list iteration.

**Watch for:** The database's `_commit_lock` protects only the commit timing check but not the cursor operations themselves, so concurrent writes from multiple threads will still race on the shared cursor (likely — SQLite with `check_same_thread=False` and WAL mode tolerates this for single-writer workloads, but multi-thread INSERT+SELECT interleaving can produce "database is locked" under load). The `should_deauth` method in `SignalTargeting` still hardcodes `-80` rather than using `self.rssi_threshold`, creating a threshold inconsistency between the two deauth-decision paths in the orchestrator (confirmed). The rogue AP `stop()` called from within `start()` on failure flushes all iptables rules unconditionally via `iptables -F`, which wipes host firewall state unrelated to this engine (confirmed).

**Verdict**: APPROVED

## High-level view

The database gains a `_commit_lock` around the batched-commit check, which prevents double-commits but doesn't serialize cursor access. Under the framework's actual usage pattern (single sniff thread + background recon thread + deauth thread all writing), SQLite's WAL mode will likely tolerate this, but concurrent execute+fetchall interleaving can corrupt result sets under high write concurrency.

The `should_deauth` vs `should_deauth_with_rssi` threshold divergence remains: the orchestrator calls both as fallback paths, but they use different thresholds (`-80` hardcoded vs `self.rssi_threshold` defaulting to `-70`). A client at -72 with no live RSSI samples would fail `should_deauth` (returns -100 average) but pass `should_deauth_with_rssi` via the DB value. The orchestrator's fallback logic handles this correctly in practice, but any caller using only `should_deauth` gets a threshold that ignores configuration.

The rogue AP `start()` gained a try/except that calls `self.stop()` on failure, providing rollback. One edge case: `_setup_iptables` runs `iptables -F` unconditionally (not scoped to the AP's interface chain), so a failed startup that got past interface config but failed at hostapd will flush the host's entire iptables ruleset during rollback — even if the AP never inserted rules.

## `should_deauth` threshold inconsistency

The orchestrator's client filtering loop first calls `should_deauth(client_mac)` which checks `avg > -80` (hardcoded), and if that fails, falls back to `should_deauth_with_rssi(client_mac, rssi)` which checks `rssi > self.rssi_threshold` (configurable, default -70).

```python
# orchestrator.py
if self.signal_filter.should_deauth(client_mac):
    close_clients.add(client_mac)
elif rssi is not None and self.signal_filter.should_deauth_with_rssi(client_mac, rssi):
    close_clients.add(client_mac)
```

```python
# signal_targeting.py
def should_deauth(self, client_mac):
    avg = self.get_avg_rssi(client_mac)
    return avg > -80  # hardcoded

def should_deauth_with_rssi(self, client_mac, rssi):
    return rssi > self.rssi_threshold  # configurable
```

Anyone constructing `SignalTargeting(rssi_threshold=-60)` expecting tighter filtering will still see `should_deauth` pass clients at -65. The `filter_targets()` method uses yet another threshold parameter (`rssi_limit=-80` default), creating three different threshold sources in one class.

## Database thread safety partial fix

```python
def _maybe_commit(self):
    now = time.monotonic()
    with self._commit_lock:
        if now - self._last_commit >= COMMIT_INTERVAL:
            self.conn.commit()
            self._last_commit = now
```

This prevents two threads from calling `conn.commit()` simultaneously, but doesn't prevent two threads from interleaving `cursor.execute()` calls, or one thread executing while another calls `fetchall()`. The more dangerous race: thread A executes a SELECT, thread B executes an INSERT before thread A calls fetchall — thread A's cursor position is now undefined. Under the framework's architecture (high-frequency packet handler inserting APs/clients, background recon doing the same, orchestrator querying) this race is reachable under load.

## Rogue AP iptables flush on rollback

```python
# rogueap.py stop() - Linux cleanup
subprocess.run("iptables -F".split(), ...)
subprocess.run("iptables -t nat -F".split(), ...)
```

These commands flush *all* rules in the filter and nat tables. If `start()` fails before `_setup_iptables()` (e.g., hostapd failure at the process spawn), the rollback calls `stop()` which still flushes everything despite the AP never having added rules. A flag like `self._iptables_configured = True` set after `_setup_iptables()` completes, checked in `stop()`, would scope the cleanup correctly.
