# Audit hardening: error handling, platform checks, EAPOL expansion, and RSSI pipeline

This change addresses Phase 3 of a code audit across the POSFramework attack toolkit. The primary work adds exception handling around network I/O calls (`sendp`, database reads), introduces Windows platform warnings for modules that depend on raw sockets, enhances the EAPOL handshake classifier to recognize group key and FT reassociation exchanges, and threads RSSI data from the database through the signal targeting and deauth pipeline. The orchestrator's `stop()` is rewritten as a loop-and-catch pattern, and attack timing is logged.

**Watch for:** The `get_clients_for_bssid` return type changed from `[mac, ...]` to `[(mac, rssi), ...]` but two callers (`deauth.add_pos_targets_from_db` and `main.py`) were not updated — they'll insert tuples into the deauth target set, causing `sendp` to receive a tuple instead of a MAC string at runtime (confirmed). The orchestrator's `stop()` joins *every* thread in the process (including the main thread) which will always hit the timeout and add unnecessary delay (confirmed). The outer exception handler in the deauth loop sets `self.running = False` and breaks on *any* error, meaning a transient OS error kills the entire deauth engine permanently rather than retrying (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

The RSSI data flow was threaded end-to-end: the database query now returns `(mac, rssi)` tuples, the orchestrator unpacks them for signal filtering, and `SignalTargeting` gained a `should_deauth_with_rssi` fallback path. The type change propagated correctly through orchestrator and signal_targeting but broke two other callers that still expect plain MAC strings.

The EAPOL classifier now handles group key handshakes (returning message numbers 5/6) and correctly parses the pairwise bit to distinguish 4-way from group-key exchanges. The non-standard message numbers 5/6 could pollute the `_eapol_tracker` set and trigger false "FULL HANDSHAKE" detections if group key frames arrive between 4-way exchanges.

Error handling wraps `sendp` calls in try/except throughout deauth, karma, and beacons. The deauth engine's outer catch terminates the loop permanently on any exception, which is more aggressive than the karma engine's approach (sleep and retry) and inappropriate for a long-running attack loop.

The orchestrator teardown was refactored to a list iteration with per-engine exception handling, but the subsequent `threading.enumerate()` join loop is overbroad and includes threads the orchestrator doesn't own, adding up to 10s of unnecessary shutdown delay.

1. **`get_clients_for_bssid` type mismatch in deauth and main.py** — `add_pos_targets_from_db()` and `main.py` pass the raw list of `(mac, rssi)` tuples into `_targets[bssid].update(...)`, inserting tuples instead of MAC strings. Extract `mac` from each tuple before adding.

Use the karma pattern: log, sleep, continue.
3. **`threading.enumerate()` join in `stop()` is overbroad** — Joins every thread in the process including unrelated ones (logging, garbage collection, the main thread itself). This adds up to 10 × 1s = 10s of pointless timeout waiting. Track spawned threads explicitly or limit to daemon threads with known prefixes.
4. **Redundant `import threading` inside `stop()`** — `threading` is already imported at module level; the local re-import is dead code (harmless but confusing).
5. **`should_deauth_with_rssi` ignores configured threshold** — The method hardcodes `-80` instead of using `self.rssi_threshold`. This diverges from the instance's configured sensitivity.

## RSSI pipeline and type contract breakage

The database method `get_clients_for_bssid` was changed from:

```python
# Before
self.cursor.execute('SELECT mac FROM clients WHERE associated_bssid = ?', (bssid,))
return [row[0] for row in self.cursor.fetchall()]
```

to:

```python
# After
self.cursor.execute('SELECT mac, rssi FROM clients WHERE associated_bssid = ?', (bssid,))
return [(row[0], row[1]) for row in self.cursor.fetchall()]
```

The orchestrator correctly unpacks the new format:

```python
for client_mac, rssi in all_clients_data:
    all_clients.add(client_mac)
```

But `deauth.py` line 62 still does:

```python
clients = db.get_clients_for_bssid(bssid)
self._targets[bssid].update(clients)  # inserts ('aa:bb:cc:dd:ee:ff', -72) as a set element
```

And `main.py` line 169:

```python
clients = self.db.get_clients_for_bssid(target_bssid)
self.deauth.add_target(target_bssid, set(clients))  # same problem
```

When the deauth loop later iterates `for client_mac in list(clients)`, `client_mac` will be a tuple. The Dot11 frame constructor expects a string MAC address — this will either crash or produce malformed frames.

## Deauth loop failure semantics

The deauth engine's `_deauth_loop` wraps the entire iteration in try/except:

```python
except Exception as e:
    log.error(f"Deauth loop error: {e}")
    self.running = False
    break
```

Compare with karma's approach:

```python
except Exception as e:
    log.error(f"KARMA beacon loop error: {e}")
    if not self.running:
        break
    time.sleep(1)  # Prevent tight error loop
```

Karma checks whether the stop was intentional and otherwise backs off and retries. The deauth engine permanently terminates on any exception that escapes the inner `sendp` try/except — for instance, if `self._targets` is mutated from another thread during `list(self._targets.items())` (a `RuntimeError` in some Python versions). For a long-running attack loop, the karma pattern is more resilient.

## Orchestrator teardown thread join

```python
import threading  # redundant — already at module top
for thread in threading.enumerate():
    if thread != threading.current_thread():
        thread.join(timeout=1)
```

`threading.enumerate()` returns all alive threads in the process, including the main thread (if `stop()` is called from a background thread) and any threads from imported libraries. The engines already join their own threads in their `stop()` methods (e.g., `deauth.stop()` does `self._thread.join(timeout=5)`), making this second pass redundant for well-behaved engines and harmful for foreign threads.

## EAPOL group key message number pollution

The enhanced classifier returns 5 and 6 for group key handshake messages. The `_eapol_tracker` in `recon.py` tracks message numbers per `(client_mac, bssid)` and triggers "FULL HANDSHAKE" when `len(set) >= 4`. If a group key message arrives between 4-way messages, the set becomes e.g. `{1, 2, 5, 3}` — length 4, triggering a false positive. The tracker should either filter to `msg_num <= 4` before inserting, or the completeness check should verify `{1, 2, 3, 4}.issubset(...)`.

## `should_deauth_with_rssi` threshold divergence

```python
def should_deauth_with_rssi(self, client_mac, rssi):
    return rssi > -80
```

The constructor accepts `rssi_threshold` (defaulting to `-70`) and `get_priority` uses it, but all deauth methods hardcode `-80`. If someone constructs `SignalTargeting(rssi_threshold=-60)`, the priority method respects it but the deauth methods don't. The new method should use `self.rssi_threshold` or at minimum document the intentional divergence.
