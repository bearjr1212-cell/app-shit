# Chip detection pipeline and live tshark decryption — v2 re-review

The five issues from the v1 review have been addressed: PSK goes to a temp file (mode 0600), data lists are `deque(maxlen=10000)`, the dead `db.log_decrypted_event` call falls through to `log.debug()`, `atexit.unregister(self.cleanup)` fires on successful disable, and signal handler registration failure logs at `log.warning`.

Watch for: The key file is passed to tshark via `-o uat:80211_keys:"<filepath>"` which treats the path as a literal key entry, not a file reference — tshark will silently fail to decrypt (confirmed). The fallback path still passes the raw PSK on the command line when temp file creation fails, re-introducing the process-list exposure without warning (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

The key file mechanism intends to keep the PSK off the process table, but the tshark invocation uses a syntax that doesn't load keys from a file. The `-o uat:80211_keys:"<path>"` flag makes tshark interpret the file path as a literal key-type/value pair. The correct approach is either to place the file at the profile's `80211_keys` UAT path and pass `-C <profile>`, or to read the entries back from the file and pass each as a separate `-o` argument (which puts secrets back on the CLI, defeating the purpose).

The fallback when `_create_key_file` returns `None` reverts to passing the PSK directly on the command line. Because the primary path's tshark syntax is wrong, the only way decryption actually works in practice is through this fallback — which re-introduces the process-list exposure the fix was designed to prevent.

## tshark UAT key file syntax

The fix writes keys in UAT CSV format to a temp file:

```python
lines.append(f'"wpa-pwd","{psk}:{ssid}"')
```

Then passes the file path to tshark:

```python
cmd.extend(["-o", f"uat:80211_keys:\"{key_file}\""])
```

tshark's `-o` flag for UAT tables expects the row content inline, not a file reference. The correct inline form is:

```
-o 'uat:80211_keys:"wpa-pwd","passphrase:ssid"'
```

To use a file instead, tshark needs the keys in the profile's `80211_keys` file and invocation with `-C profilename`. The current code produces something like `-o uat:80211_keys:"/tmp/tshark_keys_abc123.txt"` which tshark parses as a single malformed key entry and silently ignores.

When the key file path is used (the intended primary path), tshark runs without decryption enabled. The only path that produces working decryption is the fallback that passes keys inline — the exact exposure the fix aimed to eliminate.

## Silent fallback to insecure mode

```python
key_file = self._create_key_file(psk=psk, ssid=ssid, wep_keys=wep_keys)
if key_file:
    self._key_file = key_file
    cmd.extend(["-o", "wlan.enable_decryption:TRUE"])
    cmd.extend(["-o", f"uat:80211_keys:\"{key_file}\""])
elif psk or wep_keys:
    # Fallback: pass keys via CLI args if temp file creation failed
    decrypt_args = self._engine.build_decrypt_args(
        psk=psk, ssid=ssid, wep_keys=wep_keys, tls_keylog=tls_keylog
    )
    cmd.extend(decrypt_args)
```

On systems where `/tmp` is read-only or a container without a writable tmpdir, `mkstemp` fails and the PSK silently appears in `ps aux`. No log message, no opt-in flag. The security posture degrades without the operator knowing.
