# Chip detection pipeline and live tshark decryption for ReconEngine

Two new subsystems bolt onto the existing recon framework: a multi-source chip detector that selects the optimal monitor-mode method per hardware, and a tshark-based live decryption engine that runs alongside scapy sniffing to parse decrypted protocol frames in real time. The chip detector probes sysfs, lspci, lsusb, ethtool, and iw, feeds results into a method selector (airmon-ng / iw / driver), and the enhanced monitor manager wraps the whole thing with retry-fallback, atexit, and signal-handler cleanup. The tshark engine accepts a PSK + SSID, spawns tshark with `-T json`, and streams parsed DNS/HTTP/DHCP/EAPOL events back through a callback into ReconEngine.

Watch for: The PSK is passed as a tshark CLI argument visible in `ps` output (confirmed). The `_handle_decrypted_data` callback writes to `self.db.log_decrypted_event` which doesn't exist yet—currently swallowed by a bare `except (AttributeError, TypeError)` (confirmed). The live decryption session's data lists (`_dns_queries`, `_http_requests`, etc.) grow without bound for the lifetime of a session (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

The chip detection layer (`chip_detector.py`) is a passive probe-then-classify system: six sources run in sequence, each filling gaps in a `ChipInfo` dataclass, after which a `MonitorMethodSelector` maps driver names to priority-ordered lists of enable/disable methods.

The enhanced monitor manager (`monitor_manager.py`) orchestrates enable/disable through the selected methods with configurable retry, and registers atexit + SIGINT/SIGTERM handlers to guarantee cleanup. The atexit registration is unconditional and has no corresponding `atexit.unregister`, meaning the cleanup reference persists even after manual `disable_monitor_mode()`.

The tshark decryption subsystem (`tshark_decrypt.py`) operates as a parallel sniffer: it launches `tshark -T json` on the monitor interface with WPA-PSK decryption flags, reads JSON frame objects off stdout in a daemon thread, and dispatches parsed events through a callback. The PSK passes through the command line, exposing it to local process enumeration.

The data model for decrypted events has no size cap—DNS queries, HTTP requests, DHCP leases, and credentials lists all append indefinitely. On a busy network with decryption working correctly, this will grow to significant memory use over a multi-hour scan.

## PSK on the command line

`LiveDecryptionSession.start()` constructs the tshark command as:

```python
cmd: List[str] = [tshark_path, "-i", interface, "-T", "json", "-l"]
decrypt_args = self._engine.build_decrypt_args(psk=psk, ssid=ssid, ...)
cmd.extend(decrypt_args)
```

`build_decrypt_args` emits `-o uat:80211_keys:"wpa-pwd,<passphrase>:<ssid>"`. The full passphrase is a positional argument to the subprocess, readable by any local user via `ps aux` or `/proc/<pid>/cmdline`. On a shared machine or one running audit logging, this leaks the target network's PSK. tshark supports loading decryption keys from a preference file; writing a temporary file with restricted permissions and passing it via `-C` would keep the secret off the process table.

## Unbounded in-memory accumulation

`LiveDecryptionSession` stores extracted data in plain lists:

```python
self._dns_queries: List[Dict[str, str]] = []
self._http_requests: List[Dict[str, str]] = []
```

On a network with 100 DNS queries/second—reasonable for a busy retail LAN—a 2-hour session accumulates ~720K entries at roughly 200 bytes each, consuming ~140 MB just for DNS. Adding HTTP and DHCP compounds the issue. A capped `deque` or periodic flush to the database would bound memory.

## Database integration is a dead path

The callback in `recon.py` calls:

```python
try:
    self.db.log_decrypted_event(protocol, data)
except (AttributeError, TypeError):
    pass
```

`log_decrypted_event` does not exist on the database class. Every decrypted event silently falls into the exception handler. The entire tshark integration stores data only in the `LiveDecryptionSession` instance, which is discarded after `stop()` logs a summary. The feature's output is effectively limited to log lines.

## Monitor manager cleanup lifecycle

The atexit registration in `_register_cleanup` is a one-shot append with no balancing `atexit.unregister`. After `disable_monitor_mode()` succeeds, the atexit handler still fires at interpreter exit, keeping the manager object alive for the process lifetime and preventing garbage collection of subprocess handles and chip detector caches.

## Dead MonitorMethod command fields

`MonitorMethodSelector.select()` populates `commands_up`/`commands_down` on each `MonitorMethod` with a hardcoded `"IFACE"` placeholder:

```python
interface = "IFACE"  # Placeholder; actual interface filled at runtime
```

The placeholder is never substituted. `EnhancedMonitorManager._try_method` dispatches on `method.name` and calls internal `_enable_iw()` / `_enable_airmon()` methods that use `self.state.original_name` directly. The command lists are dead data—confusing for anyone reading the selector output, but not a runtime bug.

## Test coverage gaps

Not tested: the integration path in `recon.py`—`_start_decrypt_session()` and `_handle_decrypted_data()` have no dedicated test. The `db.log_decrypted_event` code path is untested (and broken). The `EnhancedMonitorManager` is not tested through the `enhanced_setup_monitor_mode()` wrapper in `monitor_mode.py`.
