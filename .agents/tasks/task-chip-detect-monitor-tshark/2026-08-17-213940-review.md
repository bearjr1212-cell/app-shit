# Chip detection, enhanced monitor manager, and live tshark decryption — v3 final

Adds automatic WiFi chipset detection (6-source probe: sysfs, uevent, lspci, lsusb, ethtool, iw), an enhanced monitor mode manager with chip-aware method selection and atexit/signal cleanup, and a live tshark decryption engine that runs alongside scapy recon to extract DNS, HTTP, DHCP, EAPOL, and credentials from decrypted 802.11 traffic.

The three v2 blocking issues — invalid tshark key file syntax, silent fallback re-exposing PSK, and untested key file mechanism — are resolved by removing the broken key file approach entirely. `LiveDecryptionSession.start()` now delegates directly to `build_decrypt_args()` for inline `-o uat:80211_keys:"wpa-pwd,passphrase:ssid"` flags, and emits `log.warning` informing the operator that decryption keys are visible in the process listing (a genuine tshark limitation with no workaround via CLI).

Watch for: The `_handle_decrypted_data` callback calls `self.db.log_decrypted_event()` which relies on the database object implementing a method that doesn't exist in the base schema — it falls through to `log.debug()` silently, so no data loss occurs, but decrypted events aren't persisted (possible, depends on database implementation).

**Verdict**: APPROVED

## High-level view

The key file removal is clean: `_create_key_file`, `_remove_key_file`, the `self._key_file` state, and the branching logic that split between file-path and fallback-inline code paths are all gone. What remains is a single unconditional call to `build_decrypt_args()` — the same function already tested in the unit suite — followed by the warning log. The fix removes ~60 lines of broken code and replaces it with 6 lines of correct, tested behavior.

The inline `-o uat:80211_keys:"wpa-pwd,passphrase:ssid"` format produced by `build_decrypt_args()` is the correct tshark syntax (the comma-separated key-type and value inside quotes, passed via `-o`). The test suite validates argument construction for all key types (wpa-pwd, wpa-psk hex, WEP, TLS keylog) and boundary cases (missing SSID, missing file).

## Database persistence gap for decrypted events

In `recon.py`, the decryption callback attempts to persist events:

```python
try:
    self.db.log_decrypted_event(protocol, data)
except (AttributeError, TypeError):
    log.debug(f"[DECRYPT] Stored event: {protocol}")
```

The `AttributeError` catch means if the database class never implements `log_decrypted_event`, the code silently degrades to in-memory-only storage. The `LiveDecryptionSession.get_decrypted_summary()` method returns the accumulated data and `ReconEngine.stop()` logs the summary counts — but the data won't survive process termination unless something upstream calls `get_decrypted_summary()` and persists it externally.
